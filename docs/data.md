# データ構造
## 投稿データは、JSON形式で管理されます。各投稿は以下のような構造を持ちます。

```json
{
  "device_id": "端末ID",
  "post_id": "unique-post-id",
  "nickname": "投稿者のニックネーム",
  "content": "投稿内容",
  "timestamp": "投稿日時（ISO 8601形式）",
  "imageUrl": "画像のURL（オプション）"
}
```

- **device_id**: 投稿を行った端末を識別するためのID。初回アクセス時にランダム生成され、localStorageに保存される。
- **post_id**: 各投稿を一意に識別するためのID。UUIDなどの方法で生成される。
- **nickname**: 投稿者が入力するニックネーム。必須項目。
- **content**: 投稿のテキスト内容。必須項目で、200文字以内に制限される。unicocde文字も使用可能。
- **timestamp**: 投稿が行われた日時をISO 8601形式で保存する。
- **imageUrl**: 投稿に添付された画像のURL。オプション項目で、画像がない場合はnullまたは空文字列になる。

## データ管理
- 投稿データは、**./data/posts.json**ファイルに保存されます。
- 画像は、**./data/images/**ディレクトリにサーバーサイドでリネームして保存され、投稿データのimageUrlフィールドには、その画像へのURL(リネーム済のもの)が保存されます。
- データの読み書きは、サーバーサイドで行われ、フロントエンドはAPIを通じてデータを取得・送信します。
- データの更新（新規投稿、削除など）はリアルタイムで反映されるように、WebSocketを使用してフロントエンドに通知されます。
- データの整合性を保つため、サーバーサイドで投稿データのバリデーションを行います。例えば、contentの文字数制限や、imageUrlの形式チェックなどが含まれます。
- 投稿の削除は、管理者が行うことができ、削除された投稿は**./data/posts.json**からも削除されるようにします。また、削除された投稿は、メインページからもリアルタイムで消えるようにします（WebSocketを使用）。
- 初回アクセス時にのみGETリクエストで**./data/posts.json**から投稿データを取得し、メインページに表示します。その後、新規投稿や削除などのデータ更新があった場合は、WebSocketを通じてフロントエンドに通知し、リアルタイムで更新されたデータを反映させます。
